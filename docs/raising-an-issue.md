# Raising an issue

An issue is how you tell the project something, without changing anything.
A problem, an idea for a tool, a question: each becomes a numbered item
that stays attached to the repository, can be discussed, and is closed when
it is resolved. It is the case file for the thing you noticed.

Issues are the right first step for almost everything. You do not need to
know how to fix a problem to report it, and you do not need to know how to
build a tool to ask for one.

## When to file one

| You noticed | File |
|---|---|
| A tool did something unexpected, or a document is wrong or unclear | **Something went wrong** |
| A lab task that is slow, error-prone, or could be automated | **A tool or feature we need** |
| Something you want to understand | **A question** |

If a sentence in a document is simply wrong and you know the right one, you
can skip the issue: open the file, click the pencil, fix it, and GitHub
turns that into a pull request for review.

## How to file one

1. Open the repository on GitHub and click **Issues**, then the green
   **New issue** button.
2. Pick one of the three forms. Each asks a few plain questions; answer them
   the way you would tell a colleague at the bench. Nothing technical is
   required.
3. Click **Submit new issue**. It gets a number and a page of its own.

A good issue says what you saw, where, and what you expected. The exact
words on the screen help. A screenshot helps. "It didn't work" without the
rest does not, because nobody can act on it.

## What happens next

Someone on the team reads it, usually within a few days, and replies on the
issue page. It may be answered, turned into a pull request, added to the
backlog, or closed with a reason. You are notified of every reply by email
and can keep the conversation going there. When the work lands, the pull
request that fixed it names the issue, and the issue is closed.

Issues are also where the AI assistant is pointed when it is asked to
work on something: "fix issue 14" gives it the full description in your
words, which is better than any paraphrase.

## Two cautions

- **Issues on these repositories are public.** Never paste collection
  content, donor names, accession-derived data, file paths that reveal a
  donor, or anything from a restricted collection. Describe the shape of the
  problem instead ("a 2 TB drive of photographs").
- **One thing per issue.** Two problems in one issue get half the attention
  each and can never be closed cleanly. File two.
